# Coming from draw.io or bpmn-js

`bpm` is a good next step when a visual canvas is useful but the source also needs to be versioned, reviewed, validated, rendered in CI, or generated by an agent. The repository already includes a bpmn-js-powered Diagram Editor; the difference is that the text pipeline makes the source artifact explicit and reproducible.

## The mental model

| Visual-tool habit | `bpm` equivalent |
|---|---|
| Draw shapes and connect them on a canvas | Declare typed nodes with stable IDs, then write directed edges in `.bpm` text |
| Let the canvas store layout in a visual file | Keep auto-layout by default; use `positioning: manual`, `at (x, y)`, `via`, and spacing controls when exact placement matters |
| Save a visual diagram as the primary artifact | Keep `.bpm` as the reviewable source; generate SVG, BPMN XML, draw.io XML, or editable PPTX as needed |
| Inspect problems visually | Run `bpm validate`; the JSON result exposes `errors`, `semanticErrors`, `warnings`, numeric metrics, and layout quality |
| Use bpmn-js to edit BPMN directly | Open `.bpmn` in Diagram Editor, then use **Import to Text** for an explicit preview-and-confirm conversion into `.bpm` |

## Starting from a BPMN canvas

The Diagram Editor is a separate visual authoring path inside the web app:

1. Open or create a BPMN diagram in Diagram mode.
2. Use the visual canvas to edit pools, lanes, events, gateways, activities, and flows.
3. Save/export BPMN XML or SVG when the visual model is the deliverable.
4. Choose **Import to Text** when the `.bpm` source should become the durable, reviewable artifact; supported
   pool/lane frames, node bounds, edge waypoints, ports, and port offsets are emitted as manual DSL geometry.
5. Review the generated text and the preserved/transformed/dropped conversion accounting, then explicitly confirm insertion; the editor never silently overwrites text.

This is intentionally one-shot. Diagram-mode edits and text-mode edits are not continuously synchronized, and PowerPoint edits do not round-trip into the source.

## Starting from draw.io

draw.io is a strong fit for freeform visual work and broad shape libraries. Move a diagram into `bpm` when you need a constrained grammar, stable IDs, deterministic validation, or a CI/agent workflow. For BPMN, prefer importing through the BPMN XML path when semantic preservation matters. For non-BPMN families, draw.io export is a visual interchange format and should be treated as intentionally lossy.

## Small text-first example

```text
task "Review order" as t1
gateway exclusive "Approved?" as g1
task "Ship item" as t2
event end none "Done" as e1

t1 -> g1
g1 -> t2: "yes"
t2 -> e1
```

Validate and render it with:

```bash
npm run bpm -- validate order.bpm
npm run bpm -- render order.bpm -o order.svg
npm run bpm -- export order.bpm --target pptx -o order.pptx
```

## What does not translate one-to-one

- A visual layout is not always recoverable as identical text coordinates. The import path preserves supported geometry where possible and reports both conversion warnings and structured preserved/transformed/dropped loss accounting.
- `bpm` currently supports BPMN, mind maps, flowcharts, architecture, and bounded Gantt timelines; it is not a general replacement for every draw.io shape library.
- BPMN XML is the semantic export. PPTX is an editable visual projection, not a semantic round-trip.
- `bpm` is local-first and has no hosted collaboration or workflow execution service in v1.
